## Recommendation for NOAA/GFDL: write the archive directly to Icechunk
Several of the problems in the table above come from how the NetCDF/HDF5 files are written and re-written, and a transactional store would avoid them:
- **Corrupted / incomplete HDF5 writes.** Seven source arrays are unreadable or missing data although their files exist: the six NWA hindcast-monthly arrays whose chunk index is empty (HDF5 reports 0 bytes of storage and 0 of 480 chunks, yet each file is 3-14 GB: regrid `dissic`, `talk`, `volcello`, `psm`, `q_p_2_n_Sm` and raw `vmo_rotate`), and the NWA decadal-monthly regrid `nsmz_100` init 1996-01 file (shape and attributes present, zero chunks written, 119 MB against 1.36 GB for its siblings). The pattern points to a write that was interrupted or never flushed (an inference from the evidence; we have not seen the producer's logs). With HDF5 such a file looks complete (it opens fine and has the right shape) but silently returns fill values; nothing in the file says it is incomplete.
- **Icechunk commits are atomic.** A writer either commits a snapshot, after which every chunk it references is guaranteed to exist, or it commits nothing and readers never see a partial result. An interrupted job can simply be re-run, and the previous snapshot stays valid. A half-written array cannot be published.
- **It would also remove other issues in this list** by construction: one store instead of thousands of per-variable/per-year/per-init files (P2, P3 bundled copies, P9 JSON sidecars), a chunk layout chosen once for the whole array (P1, P2: no per-year chunks that do not divide the series), one fill value per array (P8), and metadata that is part of the same transaction as the data (P4, `lead`/time encodings in P7).
- Keeping NetCDF as a delivery format is compatible with this: it can be exported from the Icechunk store.
